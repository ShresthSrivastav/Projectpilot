# Gap Analysis Report — ProjectPilot

## Current State vs. Production-Grade Autonomous Engineering System

---

### Dimension 1: Requirements Traceability

**Current State:** Requirements are parsed from a single prompt by the RequirementAgent, stored as JSON in ChromaDB. No formal requirements document is generated. No traceability matrix exists linking prompt → requirements → code → tests.

**Gap:** HIGH — No bidirectional traceability. If a requirement changes, there's no way to identify which files or tests need updating.

**Recommendation:** Generate a `REQUIREMENTS_TRACE.md` in each project linking prompts → features → files → test cases. Use the blueprint's route/table/file list as the traceability backbone.

---

### Dimension 2: Architecture Validation

**Current State:** Architecture is defined ad-hoc by the PlannerAgent LLM call. No formal architecture validation (e.g., does the generated code match the blueprint's route list, table schema, file structure). The DebugAgent's "blueprint reflection" warns about missing routes but does not enforce.

**Gap:** MEDIUM — Architecture drift between blueprint and generated code is detected but not corrected.

**Recommendation:** Add an architecture validation gate that compares generated `backend/main.py` routes against blueprint routes AND generated `database/models.py` tables against blueprint tables. Fail the gate on mismatch.

---

### Dimension 3: Dependency Management

**Current State:** `requirements.txt` is LLM-generated. Pip install is attempted once; on failure, individual packages are retried. There is no dependency conflict resolution, no version pinning audit, no vulnerability scanning.

**Gap:** HIGH — Generated projects may have conflicting or vulnerable dependencies. No SBOM (Software Bill of Materials) is generated.

**Recommendation:** Add `pip-audit` or `safety` scan in the security gate. Generate an `SBOM.md` listing all dependencies with versions and known CVEs.

---

### Dimension 4: Test Quality

**Current State:** Tests are generated by LLM (TestGenAgent), then replaced by fallback tests that import the real project. The fallback tests verify routes return HTTP 200 but do NOT verify response schemas, business logic, or edge cases.

**Gap:** MEDIUM — Tests verify endpoints exist but not that they return correct data or handle errors.

**Recommendation:** Enhance the fallback tests to verify response structure against the blueprint's route descriptions. Add negative tests (invalid input, missing auth, etc.).

---

### Dimension 5: Runtime Reliability

**Current State:** Runtime validation starts the app and checks `/health`. It does not test authentication, database connectivity, or API response correctness. The app is started on a random port and killed after 30s.

**Gap:** HIGH — Runtime validation is shallow. A project could pass runtime gates but have broken auth, missing DB tables, or silent failures.

**Recommendation:** Add multi-endpoint runtime tests: hit `/health`, then a protected route (verify 401 without token), then a data endpoint (verify 200 or proper error). Test database connectivity if a DB is configured.

---

### Dimension 6: Security Depth

**Current State:** Regex-based security scanner checks for hardcoded secrets, eval(), wildcard CORS, and dangerous packages. This is fast but shallow. The LLM-based SecurityAgent exists but is not integrated into the pipeline.

**Gap:** MEDIUM — Regex-only scanning misses context-dependent vulnerabilities (e.g., SQL injection via f-strings, XSS in returned HTML, insecure crypto).

**Recommendation:** Integrate the SecurityAgent into the pipeline gates (not just the supervisor API). Run the LLM-based scan as a final gate with a 60s timeout.

---

### Dimension 7: Documentation Accuracy

**Current State:** README.md is LLM-generated from the blueprint. The DocsGeneratorService can generate full documentation from source code. However, no verification ensures the docs match the actual generated code.

**Gap:** LOW — Documentation drift is possible but unlikely for small projects. For large projects, the README may reference endpoints or features that don't exist.

**Recommendation:** Add a documentation validation gate that reads generated docs and verifies all referenced endpoints/files actually exist in the generated project.

---

### Dimension 8: Deployment Readiness

**Current State:** Dockerfile and start.sh are generated as static templates. The DeploymentService can generate Docker/Render/Railway configs. But the generated Dockerfile may reference files that don't exist.

**Gap:** LOW — Packaging validator checks Dockerfile references exist. Deployment is always optional.

**Recommendation:** Add a `docker build` dry-run in the deployment gate to verify the Dockerfile is valid without actually building.

---

### Dimension 9: Monitoring & Observability

**Current State:** Pipeline progress is tracked via ChromaDB status updates. The dashboard service provides real-time WebSocket events. No structured logging or metrics for the generated project itself.

**Gap:** MEDIUM — The ProjectPilot system is observable, but the generated project is not. No way to know if a deployed project is healthy without manual checking.

**Recommendation:** Add a `/metrics` endpoint template to generated FastAPI projects (prometheus format). Include a health check configuration in the generated Dockerfile.

---

### Dimension 10: Self-Healing Completeness

**Current State:** Healing runs up to 3 attempts, repairs healable gates only (import, syntax, test, runtime, packaging). Non-healable gates (AI review, security) are reported but never fixed.

**Gap:** MEDIUM — Healing only addresses deterministic failures. AI review and security issues require human judgment.

**Recommendation:** For security issues, generate a `SECURITY_FIXES.md` with specific remediation steps rather than attempting auto-fix. For AI review failures, re-run with stricter prompt constraints.
